/concept

Source & Signal

Most developer portfolios are a dark page with a neon accent and a grid of cards. This one reads like a well-kept engineering notebook: calm paper-grey ground, precise ink, and one ultramarine “signal” color that means this is live, clickable, or important. Nowhere else.

The name is the logo

“Parsa” in solid ink, “Alizadeh” as an outline offset to the right, the way a line is indented in code. That typographic lockup is the brand; the PA monogram with its signal-colored corner is the short form.

Routes as labels

Every section is labeled with its real path in mono (/work, /log/…). It tells you where you are and it feels like a developer made it. No decorative 01/02/03.

One 3D moment: the Lattice

A single Three.js object on the home hero: a slowly turning wireframe lattice of points that leans toward the cursor. No 3D anywhere else. On phones and with reduced motion it becomes a static rendered poster.

Writing as publication

The blog is The Log: serif body text, notes in the margin, footnotes and real code blocks. It reads like a technical journal, not a card grid.

/tokens/color

Color: paper, ink, one signal

The neutrals lean slightly green-grey, like drafting paper. They are not warm cream and not pure grey. Ultramarine signal is the only brand color, and it covers less than 5% of any screen: links, primary actions, focus rings, the live status and the line under the active nav item. Success, warning and error colors only ever describe state.

/motion

Animation guidelines

Motion explains change: where something came from, what is now active, that an action worked. It never delays reading. One orchestrated moment on first load, then small, fast responses.

TokenValueUsed for
dur-instant100msPress, color changes, focus
dur-fast180msHover, tooltips, chips, toasts
dur-base280msSheets, menus, filter re-layout
dur-slow520msHero load sequence, page transitions
ease-outcubic-bezier(.2,.8,.2,1)Anything entering
ease-in-outcubic-bezier(.65,0,.35,1)Movement from A to B

Where motion happens

  • First load (home only, once per session): FoldText folds “Parsa” down letter by letter from a top hinge (550ms per letter, 35ms apart), “Alizadeh” follows 120ms later, then the intro and CTAs fade in and the Lattice assembles. About 900ms in total. The fold is pure CSS, so it starts on first paint before JavaScript loads, and it plays once per page load.
  • Scroll reveals: sections fade from 0.001 opacity with 12px rise, once, at 15% visibility. Lists stagger 40ms per item and cap at 6 items.
  • Page transitions: 180ms cross-fade via the View Transitions API. Project titles and article covers morph between list and detail.
  • Lattice: slow rotation (one turn per ~90s), leans toward the cursor with damping, pauses when off-screen or the tab is hidden.

Rules

  • Animate only transform, opacity and clip-path. Never width, height, top or left.
  • Content must be visible without JavaScript. Reveal states are applied by JS after hydration, never as initial CSS opacity: 0.
  • prefers-reduced-motion: reduce: no load sequence, no reveals, no parallax, Lattice replaced by the poster. Fades of 100ms or less are allowed.
  • No scroll-jacking, no smooth-scroll libraries, no custom cursor, no text scrambling, at most one self-running element per page: the home stack LogoLoop and the /work DriftWall (desktop only). Both are slow, pause on hover, have a visible pause button (WCAG 2.2.2), and sleep offscreen. With reduced motion the strip becomes a static wrapped row and the wall stands still. ScrollVelocity in the contact band moves only while the reader scrolls.
  • Nothing loops forever except the spinner, the skeleton shimmer, and the two pausable elements above.

4 · The Lattice (Three.js via React Three Fiber)

// components/three/Lattice.tsx — client component, loaded only where it will run
const LatticeCanvas = dynamic(() => import("./LatticeCanvas"), {
  ssr: false, loading: () => <LatticePoster /> });

export function Lattice() {
  const canRun = useCanRunWebGL();  // ≥1024px, fine pointer, no reduced motion,
                                   // no Save-Data, WebGL2 available
  return canRun ? <LatticeCanvas /> : <LatticePoster />;
}

// LatticeCanvas: ~1,800 points on a deformed icosahedral lattice + nearest-neighbour lines
<Canvas dpr={[1, 1.75]} gl={{ antialias: false, powerPreference: "low-power" }}
        frameloop={visible ? "always" : "never"} camera={{ fov: 35, position: [0,0,6] }}>
  <LatticePoints color={tokens.ink} accent={tokens.signal} />  // colors read from CSS vars
</Canvas>
  • One THREE.Points and one LineSegments using BufferGeometry. A tiny custom shader handles point size and distance fade. No post-processing, no textures, no model files. Target under 60KB gzipped for the chunk (import from three selectively).
  • About 6% of points use the signal color; the rest are ink at 55% opacity. Re-read the colors on theme change.
  • Pointer lean: lerp rotation toward the pointer by 0.04 per frame, max ±12°. Pause with an IntersectionObserver and on visibilitychange.
  • The poster is a pre-rendered transparent PNG/WebP of the same lattice (light and dark versions), so layout doesn't move when WebGL swaps in.

5 · Budgets and checks

  • Lighthouse mobile ≥ 95 for performance and 100 for accessibility.
  • LCP < 2.0s on 4G (the LCP element is the name, which is text, so it is fast). CLS < 0.02. INP < 150ms.
  • First-load JS for routes other than home: < 110KB gzipped. Three.js loads only on the home hero on desktop.
  • Keyboard: every action reachable, skip link to main, sheet and command menu trap focus and restore it.
  • Check contrast of every token pair in both themes; test at 200% zoom and at 320px width.

6 · Build order

  1. Tokens, fonts, theme toggle, ui/ primitives.
  2. Layout shell: header, dock, More sheet, footer, route progress.
  3. Content layer (MDX, Zod schemas, reading time).
  4. Log index and article (the most-visited pages over time).
  5. Work index, project page, spec sheet.
  6. Home (poster first), About, Stack, Contact with route handler, 404.
  7. The Lattice, view transitions and load sequence last, behind the fallbacks that already work.

The order is a real dependency chain: each step uses what the earlier ones built.
